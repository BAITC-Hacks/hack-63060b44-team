# HackAlem AI: почасовой прогноз ветропарка

Команда «Мы сюда случайно». Воспроизводимый Python CLI для двух турбин, с горизонтом 1–48 часов, операционными архивами NOAA GFS, временной валидацией и журналом решений оркестратора. Числа рассчитывают persistence и ExtraTrees с фиксированным seed. LLM для числовых прогнозов не используется.

Материалы сдачи: [манифест передачи и размеры](docs/handoff.md), [проверки перед сдачей](reports/submission/checks.md), [численные результаты](reports/results.md). Сценарий демонстрации на 3–5 минут приведён ниже. Большие локальные данные не входят в Git и не упакованы автоматически.

## Установка

Для зафиксированного окружения нужен **Python 3.12+**; проверено на Windows с Python 3.12.14. Из корня репозитория:

```powershell
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.lock
.venv\Scripts\python -m pip install --no-deps -e .
```

На Linux/macOS замените `.venv\Scripts\python` на `.venv/bin/python`. [requirements.lock](requirements.lock) фиксирует версии проверенного окружения; его NumPy/SciPy требуют Python ≥3.12. Альтернатива для Python 3.11 или новой платформы: `python -m pip install -e ".[test]"` с диапазонами версий из `pyproject.toml`; это уже другое окружение, его версии попадут в манифесты. ecCodes нужен для первоначального чтения GRIB; на проверенной Windows установка wheel сработала. Если на другой платформе wheel не содержит нативную библиотеку, установите ecCodes по [официальной инструкции](https://confluence.ecmwf.int/display/ECC/ecCodes+installation).

Ключи API и секреты не требуются. `requests` поддерживает стандартные переменные окружения `HTTPS_PROXY` и `REQUESTS_CA_BUNDLE`; не сохраняйте учетные данные прокси в конфигурации. Локальные данные, кэш и модели исключены из Git.

```powershell
.venv\Scripts\python -m windforecast init-data --turbine-1 "C:\Users\k4lm\Desktop\Dataset HackAlemAI для участников 11.03.2023-28.02.2026 - turbine 1.csv" --turbine-2 "C:\Users\k4lm\Desktop\Dataset HackAlemAI для участников 11.03.2023-28.02.2026 - turbine 2.csv"
.venv\Scripts\python -m windforecast audit
```

`init-data` копирует исходные файлы в `data/raw/`, не изменяет оригиналы и отказывается перезаписывать другое содержимое. Все команды по умолчанию используют [config.example.json](config.example.json). Для своей конфигурации скопируйте его в `config.local.json` и передайте `--config config.local.json` **перед** подкомандой. Относительные пути считаются от каталога конфигурации.

## Время, цель и допущения

- Часовой пояс CSV не указан. Принят фиксированный `UTC+05:00` на всём диапазоне (`data.timezone`). Это допущение о часах регистратора, а не утверждение об историческом гражданском времени Казахстана. Нужна проверка у организаторов; неверный сдвиг изменит выравнивание с погодой. Поддерживается явная IANA-зона, неоднозначное время отклоняется.
- Метка CSV считается началом десятиминутного интервала; измерение доступно после его конца. Оригинальные журналы доставки неизвестны. Для новых партий сохраняется реальное `received_at`; задним числом они не становятся доступными.
- Цель — средняя нормализованная мощность за час `[t,t+1h)`, минимум **5 валидных значений из 6**. Диапазон `[0,1]` подтвержден числами в файлах. Пропущенные, бесконечные и выходящие за диапазон значения не участвуют в цели, их число отражается в аудите/манифесте. Некорректный текст вместо числа вызывает ошибку чтения. Нули сохраняются. Пропуски не превращаются в нули и не интерполируются.
- Номинальные мощности и определение знаменателя нормализации отсутствуют. `farm_proxy=(turbine_1+turbine_2)/2` — **равновесный нормализованный индекс**, не МВт или МВт·ч. Исторический индекс существует только при наличии обеих целей.
- Принятый в проекте момент ежедневного выпуска — **23:00 UTC+05:00 = 18:00 UTC**; PDF не фиксирует час выпуска. Целевые начала часов: `issue+1h … issue+48h`, горизонты 1…48. Выпуск 31 января покрывает 1–2 февраля; последующие выпуски сдвигаются на сутки. Час, начинающийся ровно в момент выпуска, намеренно не является целью. Последний выпуск 28 февраля включает 1–2 марта.
- На момент выпуска доступны только полностью завершённые часы и полученные измерения. В феврале входы постепенно устаревают: их возраст сохраняется, вымышленных февральских измерений нет.

При покрытии 6/6 остаются 23 667 / 24 785 часов: порог 5/6 сохраняет еще 39 / 85 часов. Основная потеря данных связана с длинными разрывами. Медианная импутация **признаков** внутри обученной модели допускается и обучается только на прошлом; она не создает отсутствующие цели.

| 2 | 43.643198 | 78.538828 | [Google Maps из PDF](https://maps.app.goo.gl/8UQMwsYavY6nLvFY8) |

Координаты извлечены из фактических перенаправлений ссылок, не угаданы. Источник — [операционный архив NOAA GFS](https://registry.opendata.aws/noaa-gfs-bdp-pds/). Данные выбираются по точному циклу расчета; API реанализа и бесшовные исторические погодные ряды не используются. Обоснование выбора, проверенные запросы, доступность и ограничения — [docs/weather-source.md](docs/weather-source.md).

По умолчанию: `grid=1p00`, ближайший узел, ветер 10 м и температура 2 м. Для обеих турбин ближайший узел **44°N, 79°E**, примерно в 54 км: погодные признаки практически общие, локальная орография и высота ступицы не представлены. Это экономный рабочий вариант, не обещание высокой точности в сложном рельефе. `grid=0p25` включает более мелкую сетку и нативные часовые шаги; `0p50` также поддерживается. Эти варианты требуют отдельной загрузки и повторной валидации, результаты для них не заявляются.

Для сеток 1° и 0,5° нативный шаг 3 часа. Почасовые **прогнозные** U/V-компоненты ветра и температура линейно интерполируются между соседними сроками одного архивного выпуска; затем вычисляется скорость. Наблюдаемая выработка не интерполируется. Все опорные сроки, включая более поздний целевой срок, должны быть опубликованы до момента выпуска нашего прогноза.

Цикл: `floor_6h(issue - 6h)`. Консервативное время доступности — максимум `run+6h` и `Last-Modified` всех использованных объектов. Проверяются заголовки HTTP, диапазоны байтов, GRIB-поля, время расчета, срок прогноза и контрольные суммы. Перезаписанный после момента выпуска объект отвергается. `retrieved_at` записывается отдельно и не подменяет историческую доступность. Это воспроизведение по сохранившемуся архиву и метаданным NOAA; оригинальных логов скачивания в январе у нас нет.

```powershell
# Сеть: сначала создать кэш необходимых выпусков.
.venv\Scripts\python -m windforecast cache-weather --start 2025-12-08 --end 2026-02-28

# Воспроизводимый прогноз только из локального кэша.
.venv\Scripts\python -m windforecast forecast --issue "2026-01-31T23:00:00+05:00" --horizon 48 --model extra_trees_weather --weather cache

# Полный последовательный конкурсный сценарий: 29 ежедневных выпусков.
.venv\Scripts\python -m windforecast replay --start 2026-01-31 --end 2026-02-28 --model auto --weather cache
```

`--weather network` скачивает только недостающие объекты; `cache` вообще не обращается к сети. Поврежденный или неполный кэш вызывает ошибку. Никакой автоматической замены отсутствующего выпуска будущим или реанализом нет. Для моделей с погодой нужны исторические выпуски обучения: выбираются последние 45 дней с известными целями внутри 180-дневного окна. Когда фактов за февраль нет, продолжают использоваться соответствующие декабрьские/январские выпуски. Первое заполнение кэша может занять несколько минут и сотни МБ.

```powershell
# Явно ограниченный режим для работы без погодного архива.
.venv\Scripts\python -m windforecast forecast --issue "2026-01-31T23:00:00+05:00" --model extra_trees --weather off
```

Этот результат маркируется `observation_only` и сам по себе не выполняет конкурсное требование погоды. Даже если для persistence или `extra_trees` погода получена и проверена, она не входит в их числовые признаки; только `extra_trees_weather` использует ее в модели.

## Модели и временная оценка

`persistence` повторяет последнюю доступную часовую мощность каждой турбины. `extra_trees` использует лаги, средние, разброс, покрытие и возраст наблюдений, целевой час/сезон и горизонт. `extra_trees_weather` добавляет архивные прогнозы скорости ветра, ее куба, температуры и возраст погодного выпуска. Отдельная регрессия для каждой турбины; индекс вычисляется после предсказания.

Обучающие примеры имитируют ежедневные выпуски в тот же час. Для каждого примера признаки обрезаны по **его** моменту выпуска, погодные признаки принадлежат его архивному циклу. Для обучения текущей модели цель должна завершиться и стать доступной до текущего выпуска. Поздние загрузки блокируются и в синтетических обучающих примерах. Импутация обучается заново внутри текущего прошлого; случайного train/test-разбиения нет. Выходы проверяются без скрытого обрезания диапазона.

```powershell
# 13 временных срезов через 7 дней: наблюдения, 1 ноября — 24 января.
.venv\Scripts\python -m windforecast evaluate --start 2025-11-01 --end 2026-01-24 --every-days 7 --weather off --output reports/validation_observations

# Ежедневная валидация с архивом: 7 выпусков, 22–28 января.
.venv\Scripts\python -m windforecast evaluate --start 2026-01-22 --end 2026-01-28 --models persistence extra_trees extra_trees_weather --weather cache --output reports/validation_weather

# Отдельный последний исторический выпуск; не менять выбор модели.
.venv\Scripts\python -m windforecast evaluate --start 2026-01-29 --end 2026-01-29 --models persistence extra_trees extra_trees_weather --weather cache --no-select --output reports/holdout
```

Метрики: MAE, RMSE, bias=`prediction-actual`, NMAE и NRMSE по допустимому масштабу `target_max-target_min=1`. Все считаются по каждой турбине и индексу, для каждого горизонта, блоков 1–24 / 25–48 и всех сроков. Сохраняются число валидных целей и покрытие. Перекрывающиеся прогнозы считаются отдельными парами `(issue,target)`; это не независимые измерения. Отсутствующие цели исключаются одинаково для всех моделей и остаются пустыми в CSV.

`evaluate` выбирает минимальный MAE индекса и сохраняет `reports/model_selection.json`. `auto` может использовать выбор только после доступности последней оценочной цели; до этого используется persistence. Изменение правил данных, параметров модели, погоды или координат также возвращает `auto` к persistence с причиной `incompatible_validation`: нужно повторить валидацию. Перенос каталога хранения не меняет совместимость. `--no-select` оставляет предыдущий выбор. Не используйте позднюю валидацию для заявлений о ранних выпусках. Оценка, на которой выбрана модель, не является независимым тестом. **Февральская оценка с текущими CSV отклоняется.**

Фактически выполненные проверки и численные результаты: [reports/results.md](reports/results.md). Короткая январская валидация и один последний выпуск дают ограниченные основания для выбора; они не гарантируют качество в феврале. При валидации поступают новые исторические измерения каждый день, а в февральском replay история мощности остается январской. Приведенные метрики не проверяют качество при целом месяце без новых наблюдений.

Цели семи январских выпусков частично пересекаются с последним выпуском. Для отдельной контрольной оценки отчет дополнительно выбирает модель только по 22–26 января: все эти цели известны раньше выпуска 29 января, и целевые часы не пересекаются. Сравнение покрытий 5/6 и 6/6 воспроизводится командой `python -m scripts.run_observation_validation`. После полного replay команды `python -m scripts.check_reproduction` и `python -m scripts.summarize_results` пересоздают компактные итоговые отчеты.

Разделение на пять выпусков и контроль построено ретроспективно из уже сохранённых прогнозов. Оно соблюдает время доступности и не имеет общих целевых часов, но не является доказательством заранее скрытого теста. На выпуске 29 января MAE индекса выбранной модели — 0,307882; на семи выпусках выбора — 0,267529 против 0,424923 у persistence. Это короткие исторические проверки, а не оценка новых сезонов.

В сохранённом replay действительно 29 выпусков и 1 392 строки `(issue,target)`, покрывающие 720 уникальных целевых часов. Из 1 392 строк 1 320 относятся к февралю и 72 — к марту. Число строк больше числа уникальных часов из-за перекрытия горизонтов. К выпуску 28 февраля последняя доступная измеренная цель заканчивается **1 февраля в 00:00 UTC+05:00** (час 31 января 23:00). Возраст входа после конца этого часа — **671 час**, как записано в `stale_hours` обеих турбин. Новый погодный прогноз при этом получается для каждого выпуска. Свежая погода не заменяет отсутствующие измерения мощности.

## Обновления и автономный цикл

```powershell
.venv\Scripts\python -m windforecast ingest --turbine turbine_1 --file data/new_turbine_1.csv

# received-at задавайте только при известном реальном времени получения.
.venv\Scripts\python -m windforecast ingest --turbine turbine_2 --file data/new_turbine_2.csv --received-at "2026-02-02T12:00:00+05:00" --recalculate-issue "2026-02-02T23:00:00+05:00" --weather network

# Живой цикл после подключения актуальных измерений: текущий час UTC.
.venv\Scripts\python -m windforecast watch --issue now --weather network --interval-seconds 60

# Проверка изменений для одного исторического момента, два прохода.
.venv\Scripts\python -m windforecast watch --issue "2026-01-31T23:00:00+05:00" --weather cache --iterations 2
```

Новые CSV могут иметь исходные русские заголовки или `timestamp,power,wind_speed,temperature`. Исходные файлы не переписываются: партии сохраняются отдельно с хешем и временем получения. Повтор тех же байтов — no-op; конфликт значений по одной метке отклоняется. Поздно полученная строка не меняет уже прошедший момент выпуска. Для нового момента её использует следующий запуск. `now` округляет текущее время вниз до начала часа UTC при каждом опросе; доступны только уже завершённые часы. Для обучаемой модели нужны хотя бы `min_train_days` дней с целями в последних `train_days`: одних январских CSV для живого запуска в сентябре недостаточно. При остановке `watch` — Ctrl+C.

Оркестратор — детерминированный агент с состояниями и явными условиями перехода: проверить входы → выбрать доступный архив → сформировать признаки → обучить/предсказать → проверить результат → сохранить. Он самостоятельно повторяет временные сетевые ошибки, останавливает неверные прогнозы, отмечает устаревшие входы и пересчитывает при изменении эффективных данных. Это исполняемая оркестрация, не LLM-чат и не неподтвержденный генератор чисел. При неизменных входах используется существующий результат; одновременно писать в один каталог результатов нельзя (PID в `.run.lock`). После аварии проверяйте, завершен ли этот PID, перед удалением оставшегося lock-файла.

Анализ результата здесь означает исполняемые проверки часов, конечности чисел, диапазона мощности, согласованности индекса и времени доступности погоды, а также учёт возраста входов. Он не вычисляет неизвестную февральскую точность и не исправляет неверный прогноз молча. Так реализуется самостоятельный цикл из PDF; PDF оставляет выбор архитектуры участникам и не требует LLM.

## Результаты и воспроизводимость

```text
windforecast/data.py          чтение, качество, часовые цели, новые партии
windforecast/weather.py       операционные циклы NOAA, GRIB, локальный кэш
windforecast/models.py        признаки с отсечением по времени и модели
windforecast/pipeline.py      агентный цикл, проверки, идемпотентность
windforecast/evaluation.py    временные срезы и метрики
windforecast/verification.py  повторное обучение из сохраненного снимка
artifacts/runs/<run_id>/       отдельный неизменяемый результат запуска
data/weather/                 исходные погодные ответы и метаданные
```

`forecast.csv`: UTC-метки `issue_time`, `target_time`, `horizon`, `turbine_1`, `turbine_2`, `farm_proxy`, `model`, `model_version`, `forecast_kind`, время и источник погодного выпуска для каждой турбины. Числовые единицы — нормализованная мощность/индекс. `forecast_kind=archived_forecast` означает, что архив получен и проверен; `model_details.feature_mode=archive_weather` указывает, что погода действительно входит в числовые признаки. Для persistence и `extra_trees` признаки остаются `observations_only`.

`manifest.json` содержит эффективную конфигурацию, версии библиотек и SHA-256 кода, хеши источников и результатов, время создания, период обучения, параметры модели, выбранную валидацию, проверки, допущения и возраст последних измерений. `hourly_inputs.csv` сохраняет реальные входы обучения и их доступность, `weather_*.csv` — погодные признаки всех обучающих выпусков, `model.pkl` — обученную модель. Источники погодных признаков связаны с raw-кэшем через манифесты и хеши. Не загружайте pickle из недоверенных источников; команда проверки pickle не открывает.

`artifacts/events.jsonl` фиксирует шаги, ошибки и повторные неизменные запуски. `replay.json` перечисляет все выпуски и их статус. По умолчанию replay останавливается при ошибке; `--continue-on-error` продолжает с явными неуспехами и ненулевым итоговым кодом. Старые успешные результаты сохраняются.

```powershell
.venv\Scripts\python -m windforecast verify-run artifacts/runs/ИМЯ_КАТАЛОГА
.venv\Scripts\python -m pytest -q
```

`verify-run` проверяет контрольные суммы, требует тот же код/версии библиотек и повторно обучает модель по сохраненным снимкам без сети. Сравнение с сохраненными числами имеет допуск `1e-12`. Для передачи полного воспроизводимого расчета передайте также `data/weather/`, `artifacts/runs/` и оригинальные CSV; они намеренно не включены в Git. Небольшие отчеты и примеры прогнозов находятся в `reports/`.
